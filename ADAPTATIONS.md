# Adaptations

The harness runs the gateway's own lifecycle code, copied unchanged from the commit in `PIN` by `scripts/vendor-gateway.sh`. Nothing under `vendor/gateway/src` is edited, except by `scripts/mutate.py`, which plants one fault at a time and restores the file afterwards. Every place the harness differs from production is listed here. If a break shows up in the harness, check this list before reporting it as a gateway bug.

1. **No HTTP layer.** Payments enter through `AgentWalletService.reserveSendOp`, with the installed runner's claim and readiness, followed by `runner.schedule`, which is what `POST /wallets/send` does. The route steps that are skipped are rate limiting, body and `Idempotency-Key` header parsing, address parsing, `to_agent_id` lookup, and the mapping to 202, 403 or 503.
2. **Signer.** Production derives each wallet key from the master seed (`seedSigner`). The harness derives deterministic test keys from the wallet index and runs the same two checks, that the wallet row matches the operation account and that the derived key matches the account. These keys hold nothing on any network.
3. **Clock and ticks.** The clock is injected. `startNanoLifecycle` is started with `tickMs` set to 2^30, so its timer never fires, and scenarios call `tickNow()`, which runs the real tick: `lifecycleTick`, `watchFinalized` and the status computation that sets `ok`, `degraded` or `blocked`.
4. **Operator settings.** The harness sets the send switch on, the pause off and the rail enabled, and sets pilot caps far above any scenario amount. The caps are not the pilot values proposed for production.
5. **Frontier record.** The harness acts as the operator and records each wallet's starting state with `initializeWalletFrontier`, evidence "harness seed".
6. **Gateway address.** `startNanoLifecycle` receives the harness key at index 0 as the gateway account.
7. **Seed data.** Tenants, agents, a two-hop delegation chain in raw XNO and an agent wallet are inserted directly into the tables, not created through routes.
8. **Fake node.** Work is a constant and never validated. In honest mode the node stores whatever block it is given, unconfirmed, and confirms it only when a scenario says so. The node does not model network consensus or ledger rules. A scenario lies by overriding single RPC answers.
9. **Gateway identity.** `initGatewayIdentity` is not called. It is not on the lifecycle path.
10. **nanocurrency-web.** The harness loads the gateway's installed copy (2.0.0) through `createRequire`. The gateway loads the same package through an ESM import.
11. **Dependencies.** `vendor/gateway` is installed with `npm ci` from the gateway's lockfile. On a machine with `omit=dev` in its npm config, the gateway's dev dependencies are skipped. The lifecycle code needs only runtime dependencies.
12. **Crash.** A crash is `process.exit(86)` inside a call to the fake node. Scenario 04 exits after the node stored the block, so the gateway never sees the answer. Scenario 09 exits once while the block is being prepared and once inside the publish call before the node stores anything. The database is a file, and the next phase reopens it in a new process with a new runner owner.
13. **Activation.** The gateway server does not install the lifecycle runner: `NANO_LIFECYCLE_ACTIVATED` in `src/payment-rails/nano-activation.ts` is false, and `server.ts` starts the lifecycle only behind it. The harness does not go through `server.ts`. It calls `startNanoLifecycle` itself, with the fake node, which is how the lifecycle code runs here although the released server never runs it.
14. **Starting blocks.** Each test account starts on its own synthetic block, `sha256("harness-start:" + address)`, with a balance the harness assigns. On a real ledger no two accounts share a previous block. An earlier version started every account on one shared block, and the fake node then answered one account's successor query with another account's block.
